# Module Template

Use this template for each module design and build-state document.

# Module Name

## Purpose

Describe what this module is supposed to cover.

## Users

List the people or roles who use this module.

## Current Features

List the features that exist right now. Keep this factual.

Suggested status labels:

- Working
- Partial
- Rough
- Broken
- Legacy
- Planned
- Unknown

## Core Workflows

Describe the main workflows users can complete today. Note where a workflow stops, jumps to another module, or depends on manual work.

## Build Status

Summarize the module's condition:

- What appears usable?
- What appears unfinished?
- What appears duplicated or inconsistent?
- What needs verification?

## Screens And UI Inventory

List the visible screens, panels, forms, tables, dialogs, dashboards, maps, controls, and status indicators.

## Links To Other Modules

Describe feature relationships to other modules.

Examples:

- A person can appear in check-in, team assignment, and resource views.
- A task can reference teams, locations, hazards, and planning objectives.
- A resource request can become part of a logistics or operations workflow.

## Desktop Experience

Describe how this module works on desktop today.

## Mobile Experience

Describe how this module works on mobile today, or whether it is desktop-only.

## Current Gaps

Capture missing features, confusing flows, inconsistent UI, incomplete screens, and known rough edges.

## Design Questions

List the questions we need to answer before redesigning or expanding the module.

## Future Design Ideas

Keep future improvements separate from the current-state record.
