# MongoDB Schema Decisions

- `work_assignments` map to strategies, not tasks.
- Task narrative, debrief, `assignment_ground`, and `assignment_air` are embedded inside task documents.
- The `resources` collection maps to `logistics_resource_status_items`; it represents status snapshots rather than raw inventory.
- `resource_requests` is the canonical incident Logistics Resource Request / ICS-213RR collection. The duplicate `logistics_resource_requests` collection is retired; use `data/db/sarapp_db/migrations/migrate_logistics_resource_requests_to_resource_requests.py` for one-time data migration only.
- PIO message lifecycle approvals are embedded on each `pio_messages` document in `approvals`; the duplicate `pio_approvals` collection is retired.
- PIO misinformation timelines are embedded on each `pio_misinformation_items` document in `timeline`; the duplicate `pio_misinformation_timeline` collection is retired.
- `intel_env_snapshots`, `intel_form_entries`, and `intel_clues` are retired legacy Intel collections. Clues are canonical `intel_items` documents with `item_type="Clue"`.
- `ics_214_logs` is the canonical incident activity-log collection. A document is a stream, and entries are embedded in `entries`. The duplicate `unit_logs` collection is retired; SQLite `ics214_streams` imports seed `ics_214_logs`.
- Use string UUID4 `_id` fields, Pydantic v2, and soft deletes.

## Terminology: "master" is overloaded — read this before the sections below

"Master" is used in this codebase along two different, unrelated axes. Keep them separate:

- **Master data** (a data-shape distinction): agency reference/roster collections (personnel, equipment, vehicles, etc.) as opposed to incident-scoped collections. This is what `MasterCollections`, the `/api/master/...` router prefix, and `master_link` mean. It applies the same way whether you're inside a local catalog or the central catalog (below).
- **Local catalog** (a topology/replication distinction): a single server's own `sarapp_master` Mongo database — the LAN server's, the cloud server's, or the desktop's built-in offline server's. There are N of these, one per install, and two local catalogs can disagree with each other.
- **Central catalog**: the one `sarapp_central_master` database embedded inside `cloud_router` (see `cloud_router_architecture.md`). There is exactly one of these, agency-wide. `get_master_db()` resolves to a local catalog everywhere except inside `cloud_router`'s own `mode="master_only"` process, where it resolves to the central catalog instead — same routers, different database.
- **Old master db**: not a third live thing — a retrospective term for "the master db" as it existed before the central catalog existed at all, when there was only ever one kind of master db (what's now called a local catalog) and no local/central split. Used when discussing migration semantics or legacy data shape, never current architecture.

## Master-Incident Record Linking

- Files: `data/db/sarapp_db/mongo/master_link.py` (`build_master_link`/`mark_orphaned`), `data/db/sarapp_db/mongo/server_identity.py` (`get_server_id`), wired into `data/db/sarapp_db/api/routers/checkin.py` (`incident_personnel` mirroring), `data/db/sarapp_db/export_import/{exporter,importer}.py`, and the one-time `data/db/sarapp_db/migrations/backfill_master_links.py`.
- Context: `cloud_router/`'s new embedded central master-catalog database (see `cloud_router_architecture.md`) means a master-catalog record (personnel, equipment, vehicles, etc.) can now exist on more than one server. An incident-local record that copies fields from a master record (e.g. `incident_personnel` mirroring `MasterCollections.PERSONNEL`) needs a durable way to say *which* master record it came from, and to notice when that master record changes elsewhere.
- Shape: an embedded `master_link` sub-document (not a separate join collection — matches the existing 1:1-pointer-embedding precedent, e.g. the GAR assessment's `template_id` back-pointer): `{master_collection, master_id, master_server_origin, central_master_id, last_synced_at, sync_state, conflict}`. `sync_state` is one of `"linked" | "conflict" | "orphaned" | "local_only"`. `master_id` may be `None` only when `sync_state == "orphaned"` (a record known to be master-derived whose specific master record can no longer be identified).
- `master_id` is always the master record's UUID `_id` — never a display-only field like `person_record`/`person_id`, which are server-local integers, not globally unique once a catalog exists on more than one server.
- `master_server_origin` records which server's local `sarapp_master` the record was first copied from, since `master_id` only resolves meaningfully on that same server (or via a future `central_master_id`, once the change-stream sync relay in `realtime_architecture_roadmap.md` is built).
- Set once, at the moment a record is first copied from a master record (`sync_state="linked"`); never overwritten by routine subsequent saves to the same incident record, so a `conflict` a sync pass already flagged isn't silently erased by an unrelated edit.
- Export/import: `master_id` only means something on the server it was copied from, so import re-resolves the link against the importing server's own local master DB (matching this same-origin check in `importer.py::_resolve_master_link`) rather than trusting the foreign id — unresolvable links become `sync_state="orphaned"` rather than a dangling reference. The export manifest's `source` block now also carries the exporting server's id (`server_id`, via `get_server_id()`) so the importer knows whether a link's origin is itself.
- `backfill_master_links.py` is the one-time migration that backfills `master_link` on `incident_personnel` documents that predate this field, matching today's weak link (`person_record`) against the local `sarapp_master.personnel` catalog; unmatched records get `sync_state="orphaned"`, and documents with no `person_record` at all (never master-derived) are left untouched rather than stubbed.
- By design, an incident's copy is a one-time download, not kept in sync after that: once `checkin.py` copies a master record's fields into `incident_personnel`, that copy is independent — it is never automatically refreshed again just because the master record changed elsewhere. (An earlier version of this work added exactly that kind of continuous reconciliation; it was deliberately removed — see "Central-Master Sync Relay" below for the broader reasoning: master-vs-incident data is a pre-filled-reference-vs-downloaded-working-copy relationship, not a replicated pair kept in lockstep.) `master_link.sync_state`/`conflict` remain in the schema for a possible future use, but nothing currently writes to them beyond the initial `"linked"` stamp at copy time.

## Central-Master Sync Relay

- Files: `data/db/sarapp_db/sync/` (`config.py`, `outbox.py`, `checkpoint.py`, `central_client.py`, `relay.py`, `loop.py`), `data/db/sarapp_db/api/routers/sync.py` (central-side receiving API, mounted only in `create_app(mode="master_only")`), wired into `BaseRepository.insert_one`/`apply_update` (`data/db/sarapp_db/mongo/repository.py`) and started by `lan_server/server_manager.py`/`cloud_server/main.py`.
- Push-on-write with a local outbox, not MongoDB change streams — see the "Server ↔ central sync" section in `realtime_architecture_roadmap.md` for why (every current deployment runs standalone `mongod`; change streams need a replica set even for one node, and still can't bridge a server offline longer than the oplog retention window, which is exactly the case this feature needs to handle).
- New collections: `SystemCollections.SYNC_STATE` (repurposed — see its docstring in `collection_names.py`; one doc per master-collection write still pending delivery, `{_id, collection, doc_id, attempts, last_error}`), `SystemCollections.SYNC_PULL_CHECKPOINTS` (one doc per syncable collection, `{_id: collection_name, last_pulled_at}`).
- **Conflict policy: pure last-write-wins by `updated_at`, no logging, no review step.** An earlier version of this added a `SYNC_CONFLICTS` log and an admin "keep existing / apply incoming" review UI for the case where an existing record was the same age or newer than an incoming one but the content differed. That was deliberately removed: two genuinely simultaneous edits to the same record (down to the same stored timestamp precision) are not a realistic case worth designing a review workflow around — whichever write has the newer timestamp wins outright, and on an exact tie the incoming write wins (see `apply_incoming`'s `>=` comparison). There is nothing left to reconcile after the fact.
- `_is_local_master_db()` in `repository.py` checks the *literal* db name `"sarapp_master"`, never the env-resolved `get_master_db()` target, specifically so a write happening inside cloud_router's own process (where that resolves to `sarapp_central_master`) never tries to relay to itself.
- `sync.config.SYNCABLE_MASTER_COLLECTIONS` currently lists `personnel` and `equipment` — extend one collection at a time as each is verified end to end, matching how `master_link` was scoped to `incident_personnel` first. Adding `equipment` required no collection-specific code at all (just the config entry plus a verification test) — the relay/outbox/pull machinery is already fully generic over collection name.
- **Deletes**: `BaseRepository.delete_one` (hard delete) relays via `relay.relay_local_delete()` → `MasterCollections.SYNC_TOMBSTONES` centrally, separate from `apply_incoming`'s own `doc.get("deleted") is True` tombstone-handling path. Two different concerns share the word "tombstone" here, worth keeping distinct: `apply_incoming` treats an incoming `deleted: true` doc as a signal to hard-delete the matching local document (used identically whether that incoming doc arrived via push or pull) — it never retains anything itself. `SYNC_TOMBSTONES` is what makes a delete *discoverable later*: the central `/push` delete handler hard-deletes the real document (via `apply_incoming`, same as everywhere else) and separately upserts a `{collection, doc_id, deleted_at}` marker there, because a literal removal with nothing left behind would be invisible to a future `/pull`'s "what changed since X" query. `/pull` merges real document changes with matching tombstone markers (each represented to the caller as a synthetic `{"_id": doc_id, "deleted": true, "updated_at": deleted_at}` doc) into one response, so the receiving server's `apply_incoming` call handles both uniformly. `equipment.soft_delete`-capable collections (`soft_deletes=True`) don't need any of this — their deletes already relay for free through the ordinary upsert path, since a soft delete is just a `deleted: true` field update under `apply_update`, picked up by the same `_relay_to_central` hook as any other field change; this tombstone machinery exists specifically for `soft_deletes=False` collections like `equipment` that do a real `delete_one`.
- An edit-after-delete race (the local copy was modified at a timestamp strictly after the deletion elsewhere) keeps the edit — last-write-wins applies the same way here as anywhere else, no special-casing.
- **Manual resync**: `data/db/sarapp_db/api/routers/sync_trigger.py` (`POST /api/sync-trigger/resync`, mounted only on `mode="full"` servers) runs `sync.loop.run_one_tick()` on demand instead of waiting for `CentralSyncLoop`'s poll interval. The desktop personnel (`ui/personnel/ui_personnel.py`) and equipment (`panels/equipment_edit_panel.py`) panels each expose this as a "Resync" button alongside Add/Delete/Import/Export.
- **Sync status**: `data/db/sarapp_db/sync/status.py::get_sync_status()` is the one place that turns outbox/checkpoint internals into a plain `{enabled, central_master_url, pending_count, last_pulled}` snapshot — exposed as `GET /api/sync-trigger/status` for API/dashboard consumers, and read directly in-process by the LAN server console (`lan_server/server_console/controller.py::sync_status()`), which is the same process as the running server once started.
- **No separate central-catalog URL to configure, anywhere (2026-10-07).** The central catalog lives inside `cloud_router`'s own process — `cloud_router/router/app.py` mounts the master-only app at `/central-master` on the exact same FastAPI app that serves `/tunnel/register`. So any server that already knows how to reach cloud_router for its tunnel (`cloud_router_url`) needs no second, manually-configured URL for central-catalog sync. `sarapp_db.sync.config.derive_central_master_url(cloud_router_url)` derives `SARAPP_CENTRAL_MASTER_URL` automatically: same host, `ws(s)://` → `http(s)://`, drop `/tunnel/register`, add `/central-master`. Both `lan_server/server_manager.py` (`SARAppServerManager.__init__`) and `cloud_server/main.py` (`create_cloud_app`) call this right after resolving their own `cloud_router_url` and set the env var for their own process before constructing `CentralSyncLoop()` — no sync happens at all for a server with no tunnel configured, same as before. (An earlier pass at this added a manual `central_master_url` setting to the LAN console before this derivation existed; that field was removed once the automatic version landed — never reintroduce it.)
- **Sync status UI**: the LAN server console's monitoring tab shows a live "Central catalog sync" status line (Disabled / "Enabled — up to date" / "Enabled — N pending"), polled off the UI thread every health-timer tick (3s) via `ServerConsoleWindow._poll_sync_status()` → `ServerConsoleController.sync_status()` → `sarapp_db.sync.status.get_sync_status()`. That status function is also exposed as `GET /api/sync-trigger/status` for any other consumer. Still needed: a per-collection "last synced" indicator on the desktop's own Edit-menu catalog editor windows (Personnel, Equipment, Vehicles, Hazard Type Library, etc. — `main.py` lines ~740-756) is a separate, larger follow-up — see `backlog.md`.
- **Shared field lists (desktop ↔ web GUI)**: `modules/personnel/catalog_io.py` and `modules/logistics/equipment_catalog_io.py` hold each collection's full field list and (for personnel) the row-mapping logic — pulled out of `ui/personnel/ui_personnel.py`/`panels/equipment_edit_panel.py` so `cloud_router/master_db/webgui.py` can reuse them for its own Export/Import rather than duplicating the column set. Deliberately import nothing from `utils/edit_window_kit.py` (which imports PySide6 at module level) — the web GUI runs inside cloud_router's process and must not gain a Qt dependency just to read a field list.

## Personnel: central-vs-local record ids (`person_record` / `person_record_master`)

- Files: `data/db/sarapp_db/schemas/personnel_schema.py`, `data/db/sarapp_db/mongo/int_id.py` (`dual_key_field`), `data/db/sarapp_db/mongo/database_manager.py` (`is_central_master_db`), `data/db/sarapp_db/api/routers/{personnel,equipment,vehicles,aircraft}.py`, `data/db/sarapp_db/api/routers/sync.py` (`_DUAL_KEY_MASTER_FIELDS`), `cloud_router/master_db/webgui.py`, `data/db/sarapp_db/migrations/rename_dual_key_fields_to_master.py`.
- This is a general pattern, not personnel-specific: `dual_key_field(db, local_field, master_field)` in `int_id.py` picks the right field for any collection given a db. Every dual-keyed collection follows `<local_field>` / `<local_field>_master`, whatever the local field happens to be named in that router — it doesn't have to be `*_record`: `equipment_record`/`equipment_record_master`, `vehicle_record`/`vehicle_record_master`, `aircraft_record`/`aircraft_record_master`, `id`/`id_master` (`hazard_types`, `gar_templates`, `canned_comm_entries`, `hospitals`), `int_id`/`int_id_master` (`objective_templates`, `strategy_templates`), `channel_id`/`channel_id_master` (`radio_channels`, in `communications.py`'s `master_router` only), `template_id`/`template_id_master` (`safety_analysis_templates`). `sync.py`'s mint-on-first-push logic is similarly a `_DUAL_KEY_MASTER_FIELDS` dict keyed by collection name, not personnel-only code. See `backlog.md` for which other master collections still need this treatment vs. which are "lockdown" (central-authoritative, no dual key needed) instead.
- Not every master collection needs this: `meeting_templates` is keyed by a user-chosen `slug` with upsert (PUT) semantics, not an auto-incrementing id, so two offline servers independently creating one is a content-naming collision, not an id-minting race — nothing for a dual key to solve, so it was deliberately left alone rather than forced into this pattern. It still needs the ordinary push/pull relay, though — "no dual key" and "no sync" are different questions. It was missing from `SYNCABLE_MASTER_COLLECTIONS` until 2026-10-09, purely an oversight (every other dual-keyed collection got added to that list as part of its own work; this one, needing no dual key, got skipped entirely instead of added plain). Added with zero collection-specific code, same as `equipment` originally — see `test_local_write_relays_for_a_slug_keyed_collection` in `test_sync_end_to_end.py`.
- `person_record` is server-local: every `sarapp_master` (one per LAN/cloud/offline server) assigns it sequentially from its own counter, same as always. It is never globally unique once more than one server exists — two servers can and will independently mint the same `person_record` value for two different people.
- `person_record_master` is agency-wide and only ever assigned by the central catalog (cloud_router's `sarapp_central_master`, `mode="master_only"`). A record created directly on central gets one immediately, at creation (`personnel.py::create_person`, via `dual_key_field()` which checks `is_central_master_db(db)`); on central, this is the only id field populated — `person_record` is left unset there, since central has no local roster of its own to key against.
- A record created offline on a LAN/cloud server has `person_record_master = None` until it syncs. The central sync-receiving endpoint (`sync.py::push`) mints the next `person_record_master` the first time it sees such a record (on `apply_incoming` result `"inserted"` or `"applied"`), and bumps `updated_at` so the assignment flows back out to every server on their next pull — no separate id-remap pass, since nothing downstream keys off `person_record_master` until it's populated.
- This is intentionally *not* the sync correlation key — that's still the document's own UUID `_id`, exactly as described above under "Central-Master Sync Relay" and in "Master-Incident Record Linking". `person_record_master` is a human-facing sequential number layered on top, not a replacement for `_id`-based identity.
- Accepted tradeoff: two servers each creating a new, unrelated personnel record offline before either syncs will produce two distinct central documents (two distinct `_id`s), each eventually getting its own `person_record_master` — i.e. real duplicates, not merged automatically. Deduping/merging duplicate personnel records is deliberately out of scope for now; see `backlog.md`.
- The central catalog's pre-existing `person_record`/`equipment_record`/`vehicle_record`/`aircraft_record` values (from before this split existed) were renamed in place to their `_master` equivalents by the one-shot `rename_dual_key_fields_to_master.py` migration — a pure field rename per collection, not a data transform, since central has only ever had one writer and those values were already safe as the agency-wide id. Local servers' own `sarapp_master` is untouched by that migration; they simply gain the new, initially-null `*_record_master` field going forward.
- `cloud_router/master_db/webgui.py`'s personnel/equipment/vehicles `CollectionSpec`s key their CRUD UI off the `_master` field (not the local field), since the web GUI runs inside the central process.

## Lockdown master collections (central-authoritative, no dual key)

- Files: `data/db/sarapp_db/api/routers/organizations.py`, `resource_types.py`, `forms.py` (`master_router` only), `data/db/sarapp_db/api/routers/tests/test_lockdown_guards.py`.
- Some master collections are admin-controlled taxonomies/templates that a field user should never create ad hoc, as opposed to the dual-key collections above (things like personnel/equipment that legitimately get created in the field, including offline). For these, there's no need for a local id at all — a local catalog is read-only/pull-only, and the central catalog is the only place writes are allowed. See `backlog.md` for the full list and which collections still need this (some don't have a central-mounted router yet at all, which is a bigger lift than adding a guard to an existing one).
- Mechanism: each write endpoint calls a small per-router `_require_central(repo_or_db)` guard built on the same `is_central_master_db()` check the dual-key pattern uses, raising `HTTPException(403)` on anything but the central catalog. Reads are untouched. This is deliberately simpler than the dual-key pattern — no new field, no migration, no sync-time minting — because nothing is ever created locally for these collections in the first place.
- Done 2026-10-07: `organizations`/`organization_types`/`rank_structures`/`ranks`/`organization_rank_structure_overrides` (all in `organizations.py`, which also owns the two audit-log collections as a side effect of its own now-guarded writes — no separate guard needed there), `resource_types`/`resource_capabilities` (`resource_types.py`, which also had its `sarapp_master`-hardcoding bug fixed in the same pass), `form_families`/`form_templates`/`form_template_versions` (`forms.py`'s `master_router`; `incident_router` — actual incident form instances — is untouched, that's ordinary incident data, not a master taxonomy).
- Accepted tradeoff: a LAN/cloud server that has never connected to the central catalog has no way to create a new organization/rank/resource type/form template locally anymore. Previously it could (just disconnected, so the record would never reach central either). Worth revisiting if initial server setup ever depends on local creation of these before first contact with central.

## Safety Risk Manager — canonical Hazard Register
- File: `data/db/sarapp_db/api/routers/safety.py` (`HazardsRepository`, `list_hazards`/`create_hazard`/`get_hazard`/`update_hazard`/`delete_hazard`), collection `IncidentCollections.HAZARDS`.
- Replaces the CAP-style severity/likelihood risk matrix with USCG SPE (Severity x Probability x Exposure) scoring: `score = severity(1-5) * probability(1-5) * exposure(1-4)`, banded 1-19 Slight / 20-39 Possible / 40-59 Substantial / 60-79 High / 80-100 Very High, each with a fixed recommended action. Score/band/action are computed server-side on write and never trusted from client input.
- A hazard stores `default_spe`, `spe_initial`, and `spe_residual`. Each is a nested object with user-authored `severity`/`probability`/`exposure` inputs and server-computed `score`/`band`/`action` outputs.
- `hazard_type_id` is optional. When a hazard is created from `hazard_types`, the backend copies matching library fields (`name -> title`, `category`, `description`, `controls`, `ppe`, `standard_safety_language -> safety_language`, `default_spe`) into the incident hazard exactly once, then the incident hazard becomes independently editable. Incident-only hazards leave `hazard_type_id` as `null`.
- Linkage is backend-managed through top-level int-list fields `op_period_ids`, `task_ids`, `team_ids`, `work_assignment_ids`, and `hazard_zone_ids`. `hazard_zones` remains a separate GIS collection; hazards store the zone ids.
- No `status`/lifecycle field and no approval-blocking gate in v1 — this was a deliberate simplification versus the old CAP ORM form (which blocked approval on H/EH residual risk); see `Design Documents/legacycode.md` for what CAP ORM data paths remain for form-export compatibility.

## GAR (Green-Amber-Red) Risk Assessment — template-driven, not a fixed model
- The stock USCG 6-factor model (free 1-10 dial per factor, no defined criteria) was deliberately rejected: it produces inconsistent scores between assessors with no audit trail of *why* a score was chosen. Scoring is instead an admin-editable **template** — groups of discrete, objective hazard rows, each offering a few point-valued options (optionally flagged as a hard No-Go) — closer to a paper ORM form (e.g. CAP's MIWGF 52) than a subjective dial. Different organizations can use different templates; none of this is hardcoded.

### GAR Templates (master library)
- File: `data/db/sarapp_db/api/routers/gar_templates.py`, collection `MasterCollections.GAR_TEMPLATES` (`"gar_templates"`) — cross-incident, admin-editable, same pattern as `hazard_types.py`.
- Shape: `groups[]` (id, name) -> `rows[]` (id, label) -> `options[]` (id, label, `points`, `no_go`). Plus `bands[]`: `{floor, label, required_reviewer}` — `required_reviewer` is free text (e.g. "Operations Section Chief," "Ground Branch Director"), never a fixed enum, since who must review a given band is organization-specific.
- `score_selections(template, selections)` in that same file is the scoring engine: sums the points of one selected option per row, and if **any** selected option has `no_go: true`, the result band is forced to `"No-Go"` (using the top band's `required_reviewer`) regardless of the point total — independent of the summed score, matching real GAR/ORM doctrine that some hazards are non-negotiable stops. It is a pure function (template dict + selections in, result out) so it is unit-tested without Mongo.
- Band selection otherwise uses the same "highest floor the score meets or exceeds wins" pattern as the hazard SPE bands above.
- One starting template, "Default GAR," is inserted by the one-time script `data/db/sarapp_db/migrations/seed_default_gar_template.py` (run manually — not auto-seeded at app boot, consistent with `hazard_types` having no built-in content either). It covers the six standard GAR factor names (Supervision, Planning, Team Selection, Team Fitness, Environment, Event Complexity) as groups, each with 2 objective sub-criteria rows. It is intentionally generic (not CAP/org-specific) — clone and edit it to build an org's own rubric (e.g. a CAP wing's MIWGF 52).
- Admin UI: `modules/admin/gar_templates/windows/gar_template_manager_window.py` (`GarTemplateManagerWindow`), reachable from Edit menu -> "GAR Template Library." A `QTreeWidget` edits groups/rows/options (points + No-Go checkbox per option), a `QTableWidget` edits bands. IDs (`g1`/`r1`/`o1`, ...) are regenerated fresh on every save — safe because assessments snapshot resolved labels/points at save time (see below), so they never depend on a template's ids staying stable across edits.

### Team GAR Assessments (per-incident)
- File: `data/db/sarapp_db/api/routers/operations.py` (`get_team_gar`/`save_team_gar`), embedded on the `teams` collection document as `gar_assessments[]` — not a separate collection, and not on `tasks`, `work_assignments`, or individual hazards.
- **Scored per team, not per task.** A task can carry multiple teams (`task.task_teams[]`), each with its own risk posture, so GAR cannot live on the task itself without a slot per team. It lives on the Team instead.
- `gar_assessments` is **append-only** — there is no separate "current" field; "current" is simply the most recent entry. This is deliberate: GAR is normally assessed once per operational period (at team briefing/activation) but can be reassessed any time conditions change, so every save must add a new entry rather than overwrite, or reassessment would destroy the prior record.
- Each entry stores `template_id` **and** a full denormalized snapshot of the resolved selections (group/row/option labels, points, no_go) plus `score`/`band`/`required_reviewer`/`no_go` — so editing a template later never rewrites the meaning of a past assessment. `POST .../teams/{id}/gar` takes `{template_id?, selections[], notes, assessed_by}`; if `template_id` is omitted it falls back to the incident's default template (`GET/PATCH .../operations/gar-default-template`, stored as `default_gar_template_id` on the incident's `IncidentCollections.INCIDENT_PROFILE` doc). A specific assessment can still override that default — needed for a multi-agency incident where a CAP team and a county SAR team each score against their own org's template.
- Each entry is tagged with `operational_period_id`, resolved server-side from the incident's active operational period at write time (via `operational_periods.get_active_period`) — never client-supplied. `null` if no period is active yet.
- Each save also appends a `GAR Score` entry to the team doc's own `audit` array (a new pattern — prior to this, `audit` only existed on `tasks`).
- Non-blocking in v1, matching the hazard SPE precedent above: a Red (or No-Go) GAR score displays the required reviewer but does not gate team/task status transitions.
- UI: `modules/operations/teams/panels/gar_editor.py` (`GarAssessmentEditor`), on `TeamDetailWindow`'s "Safety" tab (`modules/operations/teams/panels/team_detail_window.py`) — renders rows dynamically from whichever template is selected (a combo box, defaulting to the incident default or the assessment's own template). The Task Detail window's Safety tab (`modules/operations/taskings/task_detail_widget.py`) shows a read-only roll-up instead (`modules/operations/taskings/team_gar_rollup.py`, `TeamGarRollupPanel`) — one row per assigned team with its current band/score, linking out to that team's Safety tab for the actual edit.
- The Task Detail window's Safety tab also shows the task's linked hazard SPE notes (control measures, mitigation, PPE, safety message) via the now-generalized `HazardAnalysisEditor` (`modules/planning/tactics_resources/widgets/hazard_analysis_editor.py`), which takes a `link_kind` of `"work_assignment"` (default, existing caller unchanged) or `"task"`.

## Forms
- File: `data/db/sarapp_db/api/routers/forms.py`
- The model is `family -> template -> version`.
- **Family** means issuing agency such as FEMA, CAP, SAR, ICS Canada, USCG, or Custom.
- **Template** means one form within that agency's set, such as FEMA's ICS 204.
- **Version** means a specific revision of that form's layout/fields over time.
- This mirrors the existing `forms/sets/<agency>/<code>/` directory layout.
- `modules/forms_creator/services/templates.py` (`FormService`) flattens this back into one dict per template for the rest of the module.
- Incident form instances are canonical single documents in `forms`; `linked_module`/`linked_record_id` live directly on that document and there are no separate form link/revision/audit/export collections.
- Generated forms should not create durable in-app revision/export histories. If a generated PDF needs to be shared, upload it as an attachment with `owner_type="form"` and `owner_id=<incident_id>-FORM-<n>`, then store the returned attachment id on the owning form document's `attachment_ids` list (or on the owning task/IAP/other domain document when the file belongs there instead).

## Attachments
- File: `data/db/sarapp_db/api/routers/attachments.py`
- Incident-scoped document and media uploads use `IncidentCollections.ATTACHMENTS` for metadata and a per-incident Mongo GridFS bucket named `attachment_files` for bytes (`attachment_files.files` and `attachment_files.chunks`).
- Attachment metadata records include `attachment_id`, `owner_type`, `owner_id`, `category`, `filename`, `mime_type`, `size_bytes`, `checksum_sha256`, `gridfs_file_id`, `uploaded_by`, `uploaded_at`, optional `description`, and soft-delete fields.
- Domain documents should reference attachment ids rather than embedding file bytes or maintaining duplicate export/link collections.
- Deleting an attachment soft-deletes metadata by default; `purge_file=true` also removes the GridFS bytes.

## Push Notifications (FCM)
- File: `data/db/sarapp_db/api/routers/push_tokens.py`, collection `MasterCollections.PUSH_TOKENS` ("push_tokens") in `sarapp_master`.
- Master-scoped, not incident-scoped: a device's FCM token isn't tied to one incident, and field devices get shared across shifts (handoff tablets), so the collection tracks token -> current person, not token -> incident.
- Keyed and upserted by `token` (unique index), not by `person_record`. Re-registering an existing token — e.g. a different responder logging into a shared device — overwrites the existing document's `person_record`/`person_id`/`incident_id` in place rather than inserting a duplicate. This is the mechanism, not an incidental detail: it's what makes shared-device handoff work without manual cleanup.
- `person_record` is resolved server-side from `person_id`/`person_record` in the request the same way `auth_sessions._find_person` does, and is nullable — an unresolvable person (no matching `personnel` row) is tolerated, not rejected, matching how check-in already treats a missing `person_record` as non-fatal.
- Document shape: `{token, person_record, person_id, incident_id, platform, device_name, app_version, created_at, updated_at}`.
- `data/db/sarapp_db/services/push.py::send_to_person(person_record, title, body, data)` is the only sender — it looks up every token for a person and sends via `firebase_admin.messaging`, deleting any token that comes back `UnregisteredError`. It is infrastructure only; nothing calls it yet. Deciding which product events (task assignment, critical narrative, etc.) should trigger a push is a separate, later decision.
- `data/db/sarapp_db/services/firebase_client.py::get_firebase_app()` lazily initializes the Firebase Admin SDK from a service-account JSON path in `SARAPP_FIREBASE_CREDENTIALS_PATH` (never hardcoded, mirrors `mongo_client.py`'s env-var convention).

## Liaison — Reporting Board and origin back-links
- File: `data/db/sarapp_db/api/routers/liaison_reporting.py`, collection `IncidentCollections.LIAISON_REPORTING_DIGESTS` ("liaison_reporting_digests").
- The Liaison Officer (LOFR) role is controlling what information flows from incident staff to external customers, not raw CRUD on agencies. The Reporting Board is a one-way, LOFR-owned snapshot: `_pull_auto_summary()` reads the live `status`/`narrative` off an Objective (`IncidentCollections.INCIDENT_OBJECTIVES`) or the live `status`/latest embedded `narrative` entry off a Task (`IncidentCollections.TASKS`), seeds `lofr_summary` from it, and never writes back to the source. The LOFR edits `lofr_summary` and toggles `ready_to_report`; nothing else in the app reads or gates on this collection.
- Document shape: `{incident_id, int_id, source_type: "objective"|"task", source_id, source_title, auto_summary, lofr_summary, ready_to_report, last_synced_at, updated_by, updated_at}`. `int_id` is sequential per-incident like the rest of the Liaison collections (see `_next_int_id` in `liaison.py`).
- Objectives (`objectives.py`) and Tasks (`operations.py`'s task-create endpoint) both gained optional `origin_module`/`origin_id` fields so a customer request logged in Liaison can be converted directly into a real Objective or Task with a back-link to where it came from. This is the same directional-FK pattern Liaison Feedback already used (`objective_id`/`task_id`/`resource_request_id` on `FeedbackItem`), just reversed: the *new* Objective/Task points back at its Liaison origin instead of Liaison pointing at an existing Objective/Task.
- `liaison_agency_requests` gained `converted_to_type`/`converted_to_id` (set via `PATCH .../agency-requests/{id}/converted`) so the Customer Requests board can show a request has already been actioned and block converting it twice.
